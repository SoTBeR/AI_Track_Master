# Пайплайн разработки: MCP-приложение для мастеринга и сведения

Версия 1.1 · 27 октября 2026 · Лицензия Apache-2.0

## 1. Описание и принятые решения

Приложение принимает стерео-треки, стемы и многодорожечные проекты, проводит их через цепочку сведения и мастеринга с помощью собственных DSP-плагинов и отдаёт готовый результат. Процессом управляет ИИ-агент через MCP-сервер; те же операции доступны из командной строки. Главная задача — мастеринг без участия человека с максимальным качеством. Решения о параметрах принимает и проверяет встроенный движок мастеринга, а агент задаёт намерение и получает отчёт. Ядро, движок, MCP-сервер и CLI написаны на Rust и поставляются одним исполняемым файлом.

| Параметр | Решение |
| --- | --- |
| Платформы | Windows, macOS, Linux с первого релиза |
| Цель проекта | Open-source, лицензия Apache-2.0 |
| Команда | Один разработчик, код пишут ИИ-агенты, почти фуллтайм |
| Входные данные | Стерео-миксы, стемы, многодорожечные проекты |
| Интерфейсы v1 | MCP-сервер и CLI, без GUI; архитектура допускает GUI позже |
| MCP-клиенты | Любой клиент по стандарту MCP |
| Режимы агента | Автономный по умолчанию; режим с подтверждением опционально (MCP elicitation, запасной вариант через CLI) |
| ML | В обработке нет; ML для анализа (тип материала, предсказание качества) решается отдельным ADR после калибровки в M7 |
| Ключевой принцип | Агент не слышит звук, поэтому параметры подбирает и проверяет движок по измерениям |
| Главная задача | Мастеринг трека без участия человека с максимальным качеством |
| Приоритет | Качество важнее скорости: офлайн-обработка, время рендера вторично |

## 2. Архитектурные принципы

1. **Многодорожечная модель с первого дня.** Сессия состоит из дорожек, шин и мастер-шины. Обычный стерео-трек — это сессия из одной дорожки. Так сведение и мастеринг живут в одном пайплайне без переделок.
2. **Качество не зависит от агента.** Параметры обработки вычисляет и проверяет встроенный движок мастеринга (раздел 3). Агент задаёт намерение (площадка, характер звучания, референс), запускает процесс и читает отчёт. Одинаковые вход и намерение дают одинаковый результат в любом MCP-клиенте, с любой моделью и из CLI без агента.
3. **«Не навредить».** Результат не может быть хуже входа по объективным метрикам при выровненной громкости. Если проверка не пройдена, движок ослабляет обработку, а в крайнем случае отдаёт безопасный базовый вариант с предупреждением в отчёте.
4. **Качество важнее скорости.** Обработка офлайн, в 64-bit float, с передискретизацией нелинейных блоков и анализом всего трека до начала обработки.
5. **Ядро отдельно от интерфейсов.** MCP-сервер, CLI и будущий GUI — тонкие оболочки над одним API ядра.
6. **Детерминизм.** Одинаковые вход и параметры дают одинаковый результат; между платформами различия допустимы только в пределах заданных допусков.
7. **Неразрушающая обработка.** Исходные файлы не меняются. Каждое изменение создаёт версию сессии с возможностью отката.
8. **Измерения как язык агента.** Каждый инструмент возвращает метрики и пояснения, а не просто «успех».
9. **Безопасность по умолчанию.** Запись только в папку проекта, диапазоны параметров, лимиты рендеров и таймауты действуют в любом режиме.
10. **Чистая лицензия.** Только зависимости, совместимые с Apache-2.0. Крейты линкуются статически, поэтому LGPL и GPL недопустимы; MPL-2.0 допускается с записью в NOTICE. ffmpeg запускается отдельным процессом. Совместимость лицензий проверяет cargo-deny.

### Слои системы

- **core (Rust):** граф сессии, ввод-вывод аудио, офлайн-рендер, анализаторы.
- **engine (Rust):** движок мастеринга: анализ, диагностика, выбор целей, планирование цепочки, цикл оптимизации, проверка «не навредить», отчёт.
- **plugin-sdk и plugins:** Plugin SDK и встроенные плагины отдельными крейтами.
- **server (Rust, rmcp):** MCP-сервер, очередь задач, режимы автономности, защита путей записи, журнал аудита.
- **cli (Rust, clap):** команды для людей и скриптов, подтверждение планов.
- **eval:** метрики, корпуса, харнесс прогонов агента и слепых прослушиваний.
- **gui (после 1.0):** отдельный слой поверх тех же API.

### Модель процессов

MCP-сервер и CLI собираются в один исполняемый файл на Rust; для работы не нужны ни Python, ни другие среды выполнения. Тяжёлый рендер идёт в пуле рабочих потоков с перехватом паники (catch\_unwind), поэтому сбой одного рендера не роняет сервер. Внешние программы (ffmpeg) запускаются отдельными процессами. Каждая задача имеет идентификатор, статус и прогресс.

## 3. Автономный движок мастеринга

Агент не слышит звук, а модели в разных клиентах рассуждают по-разному. Поэтому решения о параметрах принимает детерминированный движок внутри приложения, а агент управляет им через намерение. Это главный компонент продукта: от него зависит качество.

### Этапы

1. **Приём и проверка.** Формат, частота дискретизации, разрядность, длительность, число каналов, тишина, DC-смещение. Невалидный вход отклоняется с понятной причиной.
2. **Анализ всего трека (первый проход).** Громкость (интегральная, кратковременная, моментальная, LRA), true peak, сглаженный спектр с перцептивным взвешиванием, динамика по полосам (crest factor, PLR), стерео по полосам (корреляция, ширина, моно-совместимость), транзиенты, разметка на части по энергии и плотности (куплет, припев, бридж).
3. **Диагностика.** Проблемы с оценкой серьёзности и уверенности: клиппинг, пережатый лимитером вход, резонансы, резкость и сибилянты, гул и инфранизкие частоты, проблемы фазы и моно, срез и «звон» высоких частот от кодеков (типично для ИИ-генераций), шум.
4. **Выбор целей.** Цели доставки (громкость, true peak, форматы) берутся из профиля площадки. Тональные и динамические цели адаптируются к материалу по его признакам; намерение агента (характер звучания, жанр) и референс-трек сдвигают цели в заданных пределах.
5. **Планирование.** Цепочка строится по шаблону: восстановление → корректирующий EQ → динамический EQ и подавление резонансов → компрессия (по полосам при необходимости) → стерео и моно низа → сатурация или клиппер → лимитер → ресемплинг → дизеринг. Блоки, для которых нет причин, не включаются. Начальные параметры вычисляются правилами из разницы между анализом и целями, с учётом разметки на части, чтобы не пережимать громкие фрагменты.
6. **Цикл оптимизации.** Рендер → измерение → целевая функция → корректировка параметров в допустимых границах. Целевая функция штрафует отклонение громкости и тонального баланса от целей, превышение true peak, потерю транзиентов и динамики сверх бюджета, добавленные искажения и ухудшение моно-совместимости. Цикл ограничен по числу итераций и времени.
7. **Проверка «не навредить».** Результат сравнивается со входом и с базовым вариантом (нормализация громкости с лимитером) при выровненной громкости. Если проверка не пройдена, движок ослабляет обработку и повторяет цикл; если и это не помогает, отдаётся базовый вариант с предупреждением.
8. **Выдача.** Экспорт во все запрошенные форматы. Для форматов с потерями файл кодируется, декодируется и проверяется повторно: true peak и артефакты после кодека. Отчёт в JSON и в читаемом виде: найденные проблемы, что сделано и почему, метрики до и после, предупреждения.

Тихих сбоев нет: при любой ошибке агент получает отчёт с причиной, а частичный результат не выдаётся за готовый.

### Роль агента

- Передаёт намерение: площадку, характер звучания, жанр, референс.
- Вызывает auto\_master. Для полностью автономной работы этого одного вызова достаточно.
- Читает отчёт и при необходимости запрашивает варианты («теплее», «громче», «бережнее к динамике»). Они переводятся в ограниченные сдвиги целей и проходят те же проверки.
- Низкоуровневые инструменты остаются для тонкой работы, но экспорт всегда проходит проверку «не навредить».

### Профили целей

Цели по площадкам и профили материала хранятся как версионируемые данные (каталог profiles/), а не в коде. Тональные цели строятся как статистика сглаженных спектров эталонного корпуса по типам материала; в репозиторий попадают только агрегированные кривые, а не аудио.

**Почему Rust (ADR-001).** Один язык и один исполняемый файл для ядра, сервера и CLI. Компилятор отсекает ошибки памяти и гонки данных в коде, который пишут агенты. Кросс-сборка и дистрибуция на три ОС проще, а будущий GUI на Tauri сможет использовать ядро напрямую. Минусы: меньше готовых аудио-библиотек, нет стабильного ABI для сторонних плагинов, а официальный SDK для MCP на Rust в таблице соответствия MCP относится к Tier 3 (поддержка части функций может быть неполной). Названия крейтов, их версии и лицензии подтверждаются в M0 через cargo-deny.

## 6. MCP-сервер и CLI

### Инструменты (tools)

| Группа | Инструменты |
| --- | --- |
| Сессия | create\_session, import\_audio, list\_tracks, get\_session\_state, list\_versions, restore\_version |
| Анализ | analyze\_track, analyze\_mix, diagnose, compare (A/B с выравниванием громкости), match\_reference |
| Обработка | list\_plugins, describe\_plugin, apply\_plugin, set\_param, route\_to\_bus |
| Высокий уровень | auto\_master (полный автономный цикл), auto\_mix, propose\_plan, commit\_plan |
| Рендер и экспорт | render\_preview, export (форматы и цели площадки, проверка после кодека), qc\_report, get\_report |
| Задачи | get\_job, cancel\_job |

Все схемы строго типизированы. Каждый ответ содержит метрики и короткое пояснение, например: пик −0.8 dBTP при цели −1.0, нужно снизить уровень на выходе лимитера.

### Ресурсы и промпты

- **Ресурсы:** пресеты, цели по платформам, отчёты анализа, история версий сессий. Цели по платформам хранятся как обновляемые данные, а не зашиты в код.
- **Промпты:** готовые сценарии (автономный мастеринг одним вызовом, сведение стемов, исправление клиппинга).

### Долгие задачи

Рендер асинхронный: инструмент возвращает идентификатор задачи, сервер отправляет уведомления о прогрессе, результат можно запросить позже. Отмена задачи корректно освобождает ресурсы.

### Режимы автономности

Приложение не управляет самим агентом. Оно контролирует то, что агент может сделать через инструменты.

- **Автономный режим (по умолчанию):** агент вызывает auto\_master, движок проходит весь цикл сам и отдаёт готовый трек с отчётом. Инструменты выполняются сразу.
- **Режим с подтверждением:** изменяющие операции идут через propose\_plan. План сохраняется и ничего не применяет. Для commit\_plan сервер запрашивает подтверждение у человека через MCP elicitation. Если клиент его не поддерживает, план ждёт одобрения командой CLI (plan approve). Она работает только в интерактивном терминале: ответ читается с управляющего терминала, а не из аргументов или stdin, флага автоматического «да» нет, и нужно ввести короткий код плана. commit\_plan без одобрения отклоняется сервером. Это защищает от ошибок и излишней самостоятельности агента, но не от враждебного агента с произвольным доступом к оболочке: такого агента нужно изолировать средствами самого клиента.
- **В обоих режимах** действуют ограничения безопасности.

### Ограничения безопасности

- Запись только в папку проекта, защита от выхода за её пределы (включая символические ссылки). Читать исходное аудио можно из любых путей, которые указал агент или человек: какие папки доступны агенту, решают пользователь и клиент. import\_audio принимает только аудиофайлы (формат проверяется по содержимому) и возвращает метрики и метаданные, а не содержимое произвольных файлов.
- Допустимые диапазоны всех параметров из схем плагинов.
- Лимиты: число рендеров на задачу, размер файлов, время выполнения.
- Исходные файлы никогда не изменяются и не удаляются.
- Журнал аудита всех вызовов инструментов.
- Подтверждения в режиме с подтверждением привязаны к конкретному плану и одноразовые.

### CLI

Команды зеркалят инструменты: session, analyze, apply, plan (propose, approve, commit), render, export, а также служебные: mcp serve, mcp install (регистрация сервера в клиентах), doctor (проверка окружения). Любую операцию агента можно воспроизвести из CLI, это упрощает отладку и тесты.

## 7. Plugin SDK и встроенные плагины

### Контракт плагина

Каждый плагин описывается манифестом и реализует единый трейт Plugin:

- идентификатор, версия, категория (анализ, сведение, мастеринг);
- схема параметров: имя, тип, диапазон, единицы, значение по умолчанию, шкала (линейная или логарифмическая). Из неё автоматически (derive-макросом и schemars) строятся схема MCP-инструмента, валидация и справка CLI;
- метод process (обработка блока аудио) и метод analyze (возврат измерений);
- задержка (latency) и хвост (tail) для корректной компенсации;
- сохранение и загрузка состояния с версией схемы и миграциями;
- описание для агента: когда применять, типичные значения, предупреждения о побочных эффектах.

### Правила DSP-кода

- В process нет выделения памяти, блокировок и системных вызовов; это проверяется в тестах аллокатором-ловушкой (например, крейтом assert\_no\_alloc).
- Вся обработка в 64-bit float; разрядность понижается только при экспорте, с дизерингом и ровно один раз.
- Нелинейные блоки (сатурация, клиппер, лимитер, детекторы компрессоров) работают с передискретизацией 4–8x на качественных фильтрах.
- Эквалайзеры поддерживают минимально- и линейно-фазовый режимы; линейная фаза на низких частотах применяется с учётом пред-звона.
- Поддержка частот дискретизации 44,1–192 кГц; результат не зависит от размера блока.
- Защита от денормалей, NaN и Inf на входе и выходе.
- Параметры сглаживаются, щелчков при автоматизации нет.

В DSP-крейтах действует `#![forbid(unsafe_code)]`. Unsafe допускается только в изолированных модулях и сопровождается тестами под Miri.

### Состав плагинов

## 8. Метрики и оценка качества

Человек не участвует в работе продукта, поэтому вся оценка качества переносится в разработку: объективные метрики, откалиброванные по слепым прослушиваниям, и жёсткие ворота в CI. Качество проверяется на шести уровнях; верхние уровни дороже, поэтому запускаются реже.

1. **Юнит-тесты DSP.** АЧХ фильтров сверяется со scipy; null-тест (нулевые параметры дают вход без изменений); линейность там, где она ожидается; стабильность при экстремальных параметрах; отсутствие NaN и Inf; одинаковый результат при разных размерах блока; алиасинг нелинейных блоков ниже порога.
2. **Измерения.** LUFS, LRA, true peak (в том числе после кодирования в форматы с потерями), PLR и PSR, тональный баланс по сглаженному спектру, сохранение транзиентов, корреляция и ширина по полосам, моно-совместимость, THD+N и интермодуляционные искажения.
3. **Детекторы проблем.** Корпус с внесёнными дефектами (клиппинг, резонанс, гул, сибилянты, срез ВЧ кодеком, инвертированная фаза) и известной разметкой. Для каждого детектора считаются полнота и точность, пороги фиксируются.
4. **Золотой набор.** Манифесты корпуса: синтетика, свободно лицензированные треки, собственные материалы, ИИ-генерации, домашние миксы, проблемный вход. Для каждого трека заданы допуски метрик и итоговый балл; падение балла блокирует слияние.
5. **Агентные eval-прогоны.** Сценарии автономного мастеринга. Оцениваются достижение целей, нарушения ограничений, стабильность между прогонами и независимость от модели: результат через разные MCP-клиенты и через CLI без агента должен совпадать.
6. **Слепые прослушивания.** Многостимульный тест в духе MUSHRA со скрытым эталоном и якорем: наш результат против базового варианта (нормализация громкости с лимитером) и против других систем автоматического мастеринга как внешних ориентиров. Громкость всех вариантов выравнивается. Значимость различий проверяется статистически, согласованность слушателей контролируется. Результаты калибруют веса целевой функции и пороги «не навредить». ABX применяется, только когда нужно проверить, слышна ли разница вообще.

**Целевые показатели релиза** (фиксируются в M0, уточняются в M7):

- интегральная громкость в пределах ±0,5 LU от цели, true peak не выше цели во всех форматах, включая форматы с потерями;
- ни один трек золотого набора не хуже базового варианта по слепой оценке;
- статистически значимое предпочтение перед базовым вариантом; ориентир — не хуже внешних систем автоматического мастеринга.

Цели по платформам (Spotify, YouTube, Apple Music, CD и т.д.) хранятся как данные в ресурсах и обновляются отдельно от кода. Актуальные значения нужно проверять при реализации, так как платформы их меняют.

## 9. Этапы разработки

Сроки ориентировочные, для одного разработчика с ИИ-агентами. Каждый этап завершается рабочим срезом и прогоном метрик. Критический путь — автономный мастеринг (M0–M7); сведение начинается только после ворот качества M7.

### M0. Основание (2 недели)

Репозиторий, лицензия, AGENTS.md, спецификация сессии, ADR по ключевым решениям, CI-матрица, пробный MCP-сервер на rmcp (stdio и проверка elicitation в реальных клиентах), формат профилей целей, целевые показатели релиза.

**Приёмка:** зелёный CI на трёх ОС; собирается один бинарник, а пробный MCP-сервер отвечает на вызов инструмента из реального клиента; целевые показатели записаны.

### M1. Ядро и базовый анализ (3–4 недели)

Аудио-ввод-вывод, граф сессии (дорожки, шины), офлайн-рендер в 64-bit float, ресемплер, LoudnessMeter, SpectrumAnalyzer, StereoAnalyzer.

**Приёмка:** LUFS, LRA и true peak проходят тестовые сигналы EBU Tech 3341 и 3342 в допуске; рендер детерминирован; чтение и запись WAV и FLAC без потерь.

### M2. Plugin SDK и базовые плагины (4–5 недель)

SDK, инфраструктура передискретизации, Gain, Pan, ParametricEQ (минимально- и линейно-фазовый), Compressor, Limiter, Dither.

**Приёмка:** все DSP-тесты зелёные; null-тест проходит; лимитер не превышает true-peak цель на корпусе; алиасинг нелинейных блоков ниже порога; в process нет аллокаций.

### M3. CLI и хранилище сессий (2 недели)

Команды анализа и обработки, версии сессий в SQLite, откат.

**Приёмка:** полный сценарий обработки стерео-файла из CLI воспроизводим; откат возвращает бит-в-бит прежнее состояние.

### M4. MCP-сервер (3 недели)

Инструменты, ресурсы, промпты, система задач, защита путей записи, журнал аудита, автономный режим по умолчанию и режим с подтверждением, mcp install.

**Приёмка:** интеграционные тесты через настоящий MCP-клиент по stdio; тесты безопасности (запись за пределами папки проекта, значения вне диапазона, лимиты, не-аудиофайлы на входе); в режиме с подтверждением commit без одобрения невозможен.

### M5. Анализ и диагностика (3–4 недели)

Двухпроходный анализ всего трека, разметка на части, динамика и стерео по полосам, транзиенты, детекторы проблем с оценкой серьёзности и уверенности, инструмент diagnose.

**Приёмка:** детекторы на корпусе с внесёнными дефектами достигают зафиксированных полноты и точности; диагностика детерминирована.

### M6. Движок мастеринга (4–5 недель)

CorrectiveEQ, DynamicEQ, ResonanceSuppressor, MultibandCompressor, MidSideProcessor, LowEndMono, Saturation, Clipper, Declipper; профили целей; планировщик; цикл оптимизации; проверка «не навредить»; выдача с проверкой после кодеков; отчёт; auto\_master.

**Приёмка:** на золотом наборе все треки попадают в цели громкости и true peak во всех форматах; ни один результат не хуже базового варианта по объективным метрикам; auto\_master проходит без участия человека на всём корпусе, включая проблемный вход.

### M7. Калибровка качества (3–4 недели)

Слепые прослушивания, сравнение с базовым вариантом и внешними системами автоматического мастеринга, калибровка весов целевой функции и порогов, ADR об ML-анализе по результатам.

**Приёмка (ворота качества):** целевые показатели релиза из M0 выполнены; результаты задокументированы и воспроизводимы.

### M8. Сведение стемов (5–6 недель)

HighPass/LowPass, Gate, DeEsser, посылы, шины, сайдчейн, AutoBalance, анализ маскировки по полосам, auto\_mix. Результат сведения проходит через тот же движок мастеринга.

**Приёмка:** eval-сценарии сведения проходят; на шинах нет клиппинга; проект из 32 и более дорожек рендерится в пределах бюджета времени из M0; по слепой оценке сведение не хуже простой суммы стемов с мастерингом.

### M9. Укрепление (3–4 недели)

Многопоточный рендер, кэш анализа, профиль «быстро» для превью, потоковая обработка длинных файлов, фаззинг парсеров, санитайзеры, закрытая бета, документация.

**Приёмка:** нет открытых критичных багов; 1000 последовательных задач без утечек памяти; рендер 10-минутного трека в режиме максимального качества укладывается в целевое время.

### M10. Релиз 1.0 (2 недели)

Публикация бинарников и установщиков, контрольные суммы артефактов, changelog, документация, примеры, CONTRIBUTING, SECURITY, шаблоны issue.

**Приёмка:** установка одной командой (Homebrew, cargo install или консольный установщик) на чистой системе каждой из трёх ОС; quickstart проходится за 10 минут.

Итого около 34–41 недели, то есть 8–10 месяцев. Если сведение перенести в 1.1, релиз 1.0 с автономным мастерингом займёт около 29–35 недель (7–8 месяцев).

## 10. Работа с ИИ-агентами

Вы единственный разработчик, а код пишут агенты, поэтому главной защитой качества становятся автоматические проверки и жёсткие правила процесса.

### AGENTS.md

Корневой файл с правилами, который читает каждый агент. Содержание:

- архитектура в нескольких абзацах и карта каталогов;
- команды сборки, тестов, линтеров и запуска eval;
- стиль кода и соглашения об именах;
- запреты: аллокации и блокировки в process, unsafe без обоснования и теста под Miri, новые зависимости без ADR, GPL-зависимости, изменение публичных схем MCP без миграции, правки сразу нескольких слоёв в одной задаче;
- определение «готово»: тесты, документация, обновлённый changelog, зелёный CI.

### Цикл задачи

1. Короткая спецификация в docs/spec: что, зачем, критерии приёмки.
2. Тесты пишутся первыми, эталон берётся из независимого источника (Python-прототип, стандарт, измерение), а не из самой реализации.
3. Реализация одним агентом, одна задача затрагивает один слой.
4. Самопроверка и ревью отдельным сеансом агента с чистым контекстом.
5. Pull request, обязательные проверки CI, слияние только при зелёных метриках.

### Что проверяете лично

- Ключевые алгоритмы: лимитер, true peak, фильтры, передискретизация, ресемплинг, динамический EQ, целевая функция и пороги проверки «не навредить». Агенты уверенно пишут DSP с тонкими ошибками.
- Публичные схемы MCP и CLI.
- Новые зависимости и их лицензии.
- Защиту путей записи и всё, что касается безопасности.

### Защитные барьеры

- Обязательные проверки: сборка на трёх ОС, тесты, clippy и cargo-deny, Miri и санитайзеры, метрические тесты.
- Падение метрик на корпусе блокирует слияние.
- Ограничение размера pull request.
- ADR на каждое архитектурное изменение, чтобы решения не терялись между сеансами агентов.

### Антипаттерны

- Просьбы «перепиши модуль целиком».
- Тесты, подогнанные под реализацию.
- Параллельные правки одного слоя несколькими агентами.
- Принятие результата без прогона метрик.

## 13. Допущения по умолчанию

Эти значения приняты, чтобы не блокировать начало работы. Их можно изменить через ADR.

- Rust stable последней версии на момент старта; Python нужен только для эталонов и скриптов оценки.
- Обработка в 64-bit float на исходной частоте дискретизации (до 192 кГц); нелинейные блоки с передискретизацией 4–8x. Режим по умолчанию — автономный, профиль по умолчанию — максимальное качество.
- Форматы: WAV и FLAC для чтения и записи; AIFF, MP3, AAC, OGG читаются встроенным декодером, а записываются через ffmpeg.
- GUI после 1.0, технология выбирается отдельно (основной кандидат: Tauri, он написан на Rust и использует то же ядро напрямую).
- Рабочее название и имя пакета выбираются в M0.
- Целевое время рендера и максимальное число дорожек фиксируются в M0 по измерениям на реальных проектах.
- Платформенные цели громкости хранятся как данные и проверяются по актуальной документации платформ.

3. Оформить ADR-001 (Rust как язык ядра, сервера и CLI) и ADR-002 (допустимые зависимости и лицензии, настройка cargo-deny). Затем поднять пробный MCP-сервер на rmcp и проверить stdio и elicitation в двух-трёх клиентах.
4. Поднять CI-матрицу: сборка Cargo workspace, тесты и пробный бинарник на Windows, macOS и Linux.
5. Подготовить корпус тестовых сигналов (синус, шум, sweep, импульс) и эталонные файлы для проверки LUFS. Начать сбор корпуса реальных треков с проблемами (ИИ-генерации, домашние миксы, клиппинг, пережатый лимитер) с допустимой лицензией.
6. Зафиксировать целевые показатели: качество релиза (раздел 8), время рендера 10-минутного трека и максимальное число дорожек; найти слушателей для слепых прослушиваний в M7.
7. Пилотная задача: чтение и запись WAV и первый анализатор LoudnessMeter по циклу «спецификация, тест, реализация, ревью». Результат пилота покажет, насколько процесс с агентами работает, до того как на нём строится всё остальное.
